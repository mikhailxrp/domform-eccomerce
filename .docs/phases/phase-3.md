# Phase 3 — Онлайн-оплата и касса

## Цель

Покупатель, выбравший на оформлении «Картой на сайте», после создания
Заказа видит страницу-заглушку оплаты (без реального списания),
поясняющую, что это демо-проект, и предлагающую связаться с Менеджером;
Менеджер получает готовый механизм фиксации предоплаты/остатка (без
собственного UI — UI добавится вместе с Панелью менеджера в Фазе 4) —
`FR-PAY-001…004`.

Не входит: `FR-PAY-005` (фискализация Атол) — не реализуется в
портфолио-версии (`ADR-018`, `Q-007` снят как нерелевантный); реальная
интеграция с ЮMoney — тоже не реализуется (`ADR-018`); UI Менеджера для
`FR-PAY-002` (кнопка «Отметить оплату» в Панели) → Фаза 4, когда
появится сама Панель менеджера.

## Статус

✅ Завершена

## Решения фазы

- **`FR-PAY-002` разрезан на механизм и UI, как `FR-ORD-002/003` в
  Фазе 2 (`phase-2.md` → «Решения фазы»).** Панели менеджера, где
  Менеджер физически нажимает «оплата получена», до Фазы 4 нет.
  Фаза 3 строит функции `markOrderPrepaid()` / `markOrderPaidFull()`
  в `Models/Order.php` — единственные места, пишущие
  `orders.payment_status`, — и чистую валидацию суммы в
  `Core/Payment.php`. Вызов из Панели управления — Фаза 4, без
  изменений в самих функциях.
- **Реальной интеграции с ЮMoney нет.** «Картой на сайте» ведёт на
  собственный `/payment/stub`, оформленный в стиле экрана оплаты — без
  редиректа на провайдера, без вебхука, без записи в `payment_logs`
  (таблица остаётся в схеме для возможного реального провайдера в
  будущем, но в этой версии не используется способом `card_online`).
- **Страница заглушки без id в URL.** По тому же принципу, что
  `/checkout/success` (Фаза 2, Таск 4): `/payment/stub` резолвит Заказ
  через `$_SESSION['last_order_id']`, не через параметр маршрута —
  иначе Гость мог бы подставить чужой id и увидеть чужой Заказ.
- **`FR-PAY-003` (защита от повторного платежа) новых задач не
  создаёт.** Часть, применимая без реального провайдера — защита формы
  оформления от двойной отправки — уже сделана в Фазе 2 Таском 4
  (`checkout_token` + `tooManyAttempts('checkout', ...)`). Часть про
  идемпотентность вебхука неприменима — вебхука нет.
- **`FR-PAY-004` (обработка отказа банка) не реализуется отдельной
  веткой.** Реального вызова провайдера нет, значит нет и отказа банка
  для обработки — `pay.md` п.4 прямо фиксирует это как N/A для
  портфолио-версии.
- **Деньги** — суммы в `markOrderPrepaid()`/`markOrderPaidFull()` и в
  `validatePaymentAmount()` только строками/`DECIMAL`, никогда `float`
  (`php.md`).

## Таск 1 — Страница-заглушка оплаты картой

**Статус:** ✅ Завершён — код реализован, проверен через `php -S` +
`curl` против реальной БД (`mikhail700.beget.tech`) и вручную в
браузере пользователем: заказ картой на сайте → кнопка «Перейти к
оплате» на `/checkout/success` ведёт на `/payment/stub` без id в URL;
заказ наличными/переводом → кнопки нет, прямой заход редиректит на
`/checkout/success`; без `last_order_id` в сессии → редирект на `/`;
`composer test` 119/119; тестовые заказы удалены после проверки.
Ручная проверка в браузере нашла 2 визуальных бага, не видных в HTML
(несуществующий класс `mt-30`, ссылка без визуального выделения) —
исправлены и повторно подтверждены пользователем (детали —
`dev-log.md`, `TASK.md`, 18.09.2026)

**Цель таска:**
`GET /payment/stub` показывает номер и статус текущего Заказа
(резолвится через `$_SESSION['last_order_id']`, без id в URL — как
`/checkout/success`), текст о демо-проекте и кнопку
«Позвонить/WhatsApp» (`SHOP_PHONE`/`SHOP_WHATSAPP_URL`); на
`/checkout/success` текущий текст-заглушка про оплату картой (строка
36-41 `checkout/success.php`) заменяется ссылкой на `/payment/stub`,
видимой только когда `payment_method === 'card_online'`.

**Что нужно создать/изменить:**
- `config/routes.php` — изменить: `GET /payment/stub` →
  `['PaymentController', 'stub']`
- `src/Controllers/PaymentController.php` — создать: `stub()` —
  `ensureSessionStarted()`, `last_order_id` из сессии → `findOrderById()`;
  нет id в сессии или заказ не найден → редирект на `/`; `payment_method
  !== 'card_online'` → редирект на `/checkout/success` (заглушка не для
  наличных/перевода)
- `src/Views/payment/stub.php` — создать: по образцу
  `checkout/success.php` (шапка/подвал, breadcrumbs, `flash.php`),
  номер и статус Заказа через `orderStatusLabel()`, поясняющий текст
  «демо-проект, реальное списание не производится», кнопка
  «Позвонить/WhatsApp» (`tel:` / `SHOP_WHATSAPP_URL`), ссылка «Вернуться
  к заказу» → `/checkout/success`
- `src/Views/checkout/success.php` — изменить: блок `payment_method ===
  'card_online'` (строки 36-41) — вместо текста добавить ссылку-кнопку
  на `/payment/stub`

**Definition of Done:**

## Таск 2 — Механизм фиксации оплаты (без UI)

**Статус:** ✅ Завершён — последний таск фазы, фаза 3 целиком закрыта.
Код реализован и проверен: `composer test` 125/125 (6 новых тестов
`PaymentTest`); `grep -r "SET payment_status" src/` — ровно 2
вхождения; ручная проверка временным скриптом в scratchpad против
реальной БД (`mikhail700.beget.tech`) — `markOrderPrepaid()`,
`markOrderPaidFull()`, идемпотентность и случай отменённого Заказа
подтверждены. `markOrderPaidFull()` не пишет `$amount` в БД (в схеме
нет колонки под остаток — `orders.total` уже содержит полную сумму),
значение уходит в `logInfo()` как аудиторский след (детали —
`dev-log.md`, `TASK.md`, 18.09.2026)

**Цель таска:**
Есть единственный путь пометить оплату Заказа полученной —
`markOrderPrepaid()` для предоплаты (переводит `payment_status` в
`prepaid`, заполняет `prepaid_amount`, переводит статус Заказа
`new → confirmed` через уже существующий `transitionOrderStatus()`) и
`markOrderPaidFull()` для остатка (`payment_status → paid_full`) — обе
в одной транзакции, идемпотентны (повторный вызов на уже оплаченном
Заказе не меняет ничего и не бросает исключение). Валидация суммы —
чистая функция, без БД, под unit-тест. UI вызова — Фаза 4, здесь не
реализуется; проверка — тестами и вызовом функций напрямую.

**Что нужно создать/изменить:**
- `src/Core/Payment.php` — создать: `validatePaymentAmount(string
  $amount, string $orderTotal, string $alreadyPaid): ?string` —
  `null` если сумма корректна (положительное число, не превышает
  `orderTotal - alreadyPaid`), иначе текст ошибки; сравнение только
  через `bccomp()`, никогда `float`
- `tests/Unit/PaymentTest.php` — создать: отрицательная/нулевая сумма,
  сумма больше остатка, корректная сумма, сумма с лишними знаками
  после запятой
- `src/Models/Order.php` — изменить: `markOrderPrepaid(int $orderId,
  string $amount): bool` — `beginTransaction` → `UPDATE orders SET
  payment_status='prepaid', prepaid_amount=:amount WHERE id=:id AND
  payment_status='unpaid'`; `rowCount() === 0` → уже оплачен →
  `commit()` без изменений, вернуть `false`; иначе —
  `transitionOrderStatus($orderId, 'confirmed')` (не бросает, если
  переход недоступен — Заказ мог быть отменён) → `commit`;
  `markOrderPaidFull(int $orderId, string $amount): bool` — тот же
  паттерн, `UPDATE ... WHERE payment_status='prepaid'` →
  `payment_status='paid_full'`, без смены `orders.status` (эта ось не
  управляется оплатой, см. `pay.md`)

**Definition of Done:**
- [ ] `composer test` зелёный, включая `PaymentTest`:
      `validatePaymentAmount()` отклоняет 0/отрицательную/превышающую
      остаток сумму, принимает корректную
- [ ] `grep -r "SET payment_status" src/` — единственные два вхождения
      в `markOrderPrepaid()`/`markOrderPaidFull()`
- [ ] Ручная проверка временным скриптом в scratchpad (не в репозитории)
      против реальной БД (`mikhail700.beget.tech`): Заказ `new`/`unpaid`
      → `markOrderPrepaid()` → `prepaid`/`confirmed`, `prepaid_amount`
      записана; повторный вызов → `false`, данные не изменились;
      `markOrderPaidFull()` после этого → `paid_full`,
      `orders.status` не тронут; Заказ, отменённый до вызова
      (`cancelled`) → `markOrderPrepaid()` помечает оплату, но
      `transitionOrderStatus()` не переоткрывает статус (переход
      запрещён таблицей 6.3, функция не бросает исключение)
- [ ] Деньги нигде как `float`
- [ ] Проверить `.docs/dod-global.md`
