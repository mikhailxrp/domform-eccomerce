# Модуль STOCK — Склад и остатки (Выставочный образец)

> Как это работает. Не «как написать код» — конкретные функции/классы
> определяются на `phase-init`/`task-init` для Фазы 5.
> Источник: `00-input/tz.md` разделы 6.1 (глоссарий «Резерв»,
> «Списание»), 6.3 (диаграмма статусов Заказа), 7 (UC-02), 8.9
> (`FR-STOCK-001…005`), 9 (`BR-003`, `BR-004`).

---

## Назначение и роли

В этом бизнесе нет склада в привычном смысле — обычные Варианты
изготавливаются под заказ без предела и без остатка, который можно
исчерпать (`BR-004`). Модуль STOCK целиком описывает единственное
исключение: **Выставочный образец** — 0–1 физический экземпляр
конкретного Варианта, стоящий в цеху и доступный к получению без
ожидания изготовления.

- **Менеджер / Администратор** — единственные роли, взаимодействующие
  с модулем: отмечают Вариант образцом, вручную снимают Резерв по
  истечении устно согласованного срока, обрабатывают конкуренцию за
  один образец между Покупателями.
- **Гость / Покупатель** — только читают результат (статус
  «Выставочный образец» на карточке, отсутствие остатка на всех
  экранах) — никаких прямых действий с модулем не совершают.

---

## Поток данных

1. Менеджер/Администратор включает переключатель «Выставочный
   образец» у конкретного Варианта прямо в общем списке товаров
   Панели управления (`FR-STOCK-001`) — не отдельный список, доступно
   и при создании нового Товара, и в любой момент после.
   → `product_variants.is_showroom_sample = 1`.
2. Карточка товара и фильтр каталога «В наличии» сразу отражают этот
   статус (`FR-CARD-003`, `FR-CAT-003`) — обычное чтение поля, без
   отдельного события.
3. Покупатель оформляет Заказ на этот Вариант и вносит предоплату
   (модуль `PAY`). Момент, когда предоплата **фактически получена**
   (любым способом — картой, наличными, переводом), а не момент
   оформления Заказа, — событие, которое закрепляет Резерв
   (`BR-003`, `FR-STOCK-002`).
   → создаётся строка `reserves` (`order_item_id`, `product_variant_id`,
   `status='active'`, `agreed_until` — устно согласованная дата).
4. Менеджер переводит связанный Заказ по статусам вплоть до
   «Доставлен/Собран» (диаграмма 6.3). На этом переходе — и только на
   нём — Резерв и отметка «Выставочный образец» снимаются
   **автоматически** (`FR-STOCK-004`):
   → `reserves.status = 'fulfilled'`, `released_at = NOW()`;
   → `product_variants.is_showroom_sample = 0` (образец продан,
   экземпляра больше нет).
5. Если вместо доставки Заказ отменяется (модуль `ORD`, `BR-007`) —
   Резерв снимается вручную/автоматически при отмене
   (`status='released'`), а `is_showroom_sample` **возвращается в 1**
   (раздел 6.3: «возвращается в перечень доступных»), потому что
   физический образец остаётся в цеху нераспроданным.
6. Ни на одном покупательском экране числовой остаток не
   отображается никогда (`FR-STOCK-005`) — вместо него всегда один из
   двух взаимоисключающих признаков: срок изготовления
   (`FR-CARD-002`, обычный Вариант) или статус Выставочного образца
   (`FR-CARD-003`).

## Ключевые бизнес-правила

**Резерв существует только для Выставочного образца (`BR-004`,
`FR-STOCK-002` правило 1).** У обычных Вариантов под заказ нет
физического остатка, который можно закрепить — Резерв как сущность
не появляется вне этого случая. Не путать «Резерв» с обычным
бронированием количества товара из привычных интернет-магазинов:
здесь это 0..1 запись на весь Вариант, привязанная к конкретному
`order_item`.

**Срок Резерва — устный, не системный таймер (`FR-STOCK-002` правило
2, `BR-003`).** Поле `agreed_until` хранится для справки Менеджеру, но
система не действует на его основании автоматически: не снимает
Резерв по дате, не шлёт уведомлений об истечении. Единственный
механизм снятия по истечении срока — ручное действие Менеджера в
Панели управления (`FR-STOCK-002` правило 3, UC-02 отклонение 2в).
Это осознанное решение ТЗ, не пробел — не реализовывать
автоматический cron/таймер, который ТЗ прямо исключает.

**Конкуренция решается по факту оплаты, не по факту оформления
(`FR-STOCK-003`, `BR-003`).** Если два Покупателя оформили Заказ на
один и тот же образец, побеждает тот, чья предоплата поступила
*первой по времени*, даже если его Заказ оформлен позже. Практическое
следствие для реализации: момент выигрыша фиксируется на записи в
`payment_logs`/подтверждении оплаты (модуль `PAY`), а не на
`orders.created_at`.

**Списание — не то же самое, что снятие по отмене.** Оба действия
меняют одни и те же поля (`is_showroom_sample`, `reserves.status`), но
с разным конечным состоянием: списание (`fulfilled`, доставка
состоялась) навсегда закрывает Вариант как физический экземпляр — на
его место повторно образец не ставится; снятие по отмене
(`released`) возвращает его в продажу. Не сворачивать эти два случая
в одну функцию с одним и тем же результатом.

**Показ остатка Покупателю запрещён категорически (`FR-STOCK-005`,
`BR-004`).** Это не UX-предпочтение — прямое требование бизнеса
(«под заказ — единственный способ работы», бриф п. 3.3). Ни одна
будущая доработка каталога/карточки не должна вводить числовое поле
«в наличии: N шт.».

## Граничные случаи из сценариев ТЗ (раздел 7, UC-02)

Модуль целиком выстроен вокруг отклонений UC-02 — «Покупатель
покупает Выставочный образец»:

- **2а — два Покупателя одновременно оформляют Заказ на один и тот же
  образец.** Резерв закрепляется за тем, кто первым внёс предоплату;
  второму Менеджер лично сообщает о недоступности и предлагает такой
  же Вариант под заказ (не автоматическое сообщение на сайте — звонок
  Менеджера).
- **2б — первый Покупатель оформил, но не оплатил; второй оплатил
  первым.** Заказ первого Покупателя отменяется Менеджером по
  звонку — это ручное действие, не автоматическая отмена по таймеру
  или по факту чужой оплаты.
- **2в — согласованный устно срок истёк, Покупатель не забрал
  образец и не внёс остаток.** Резерв снимается только вручную
  Менеджером в Панели управления (см. правило выше про отсутствие
  таймера) — образец снова становится доступен для продажи.

Из общего чек-листа обязательных отклонений (раздел 7, сводная
таблица) к STOCK относится ровно один пункт — «Два покупателя
претендуют на последний экземпляр» — помечен как «Разобрано»
именно через UC-02 (2а) и применим только к Выставочным образцам:
у обычных Вариантов под заказ ограниченного остатка не существует,
поэтому конкуренции в принципе не может возникнуть.

## Связанные таблицы БД

См. `.docs/database.md`:
- `product_variants.is_showroom_sample` — единственный признак
  «остатка» во всей схеме; `INDEX(is_showroom_sample)` — быстрый отбор
  образцов.
- `reserves` (`order_item_id` UNIQUE, `product_variant_id`, `status`,
  `agreed_until`, `created_at`, `released_at`) — весь жизненный цикл
  модуля. Не более одного `active`-резерва на Вариант — обеспечивается
  на уровне БД через `UNIQUE(active_variant_id)` (виртуальная
  generated column, см. `database.md`), не только проверкой в Model;
  Model перехватывает ошибку дублирования ключа при INSERT как
  проигрыш конкуренции (`BR-003`).
- Модуль не заводит собственной таблицы количеств/остатков —
  сознательное решение (`ADR-007` в `planning-log.md`), совпадающее с
  `BR-004`.

Не входит в этот модуль (пограничные, но отдельные модули):
- Фактическое получение/фиксация оплаты, которая закрепляет Резерв —
  модуль `PAY` (`.docs/modules/pay.md`).
- Переходы статуса Заказа, включая «Доставлен/Собран» и отмену,
  которые запускают Списание/снятие Резерва, — модуль `ORD`.
- Скидка на Вариант (`discount_percent`) — независимое поле, модуль
  `DISC` (Фаза 6), не пересекается с наличием образца.
