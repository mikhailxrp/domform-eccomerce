## Назначение и роли

Модуль — четыре помощника MVP плюс два помощника 2-й очереди, объединённые
одним правилом маршрутизации (`BR-AI-001`) и одним бюджетом. Ни один
помощник не находится на критическом пути покупки (`AC-06`, раздел
11.8: «ни одна ИИ-функция не блокирует основной сценарий») — это
единственная причина, по которой модуль стоит последней фазой: он
может отказать целиком без последствий для остального сайта.

**MVP (`FR-AI-001…004`):**
- **Разбор характеристик из описания** (`FR-AI-001`) — Администратор.
- **Генератор черновика описания Товара** (`FR-AI-002`) — Администратор.
- **Консультант в чате** по доставке/оплате/возврату/гарантии
  (`FR-AI-003`) — Гость, Покупатель.
- **Подбор Товара диалогом** (`FR-AI-004`) — Гость, Покупатель.

**2-я очередь, вне текущей фазы, но описаны полным форматом по
требованию раздела 8.19 (`FR-AI-005…006`):**
- **SEO-тексты для Категорий** (`FR-AI-005`) — Администратор.
- **Смысловой поиск по каталогу** (`FR-AI-006`) — Гость, Покупатель.

Два помощника из брифа («Помощник менеджера», «Фильтр отзывов») в ТЗ
намеренно не описаны требованиями — бриф не раскрывает их содержание,
и придумывать его запрещено (правило 5 системного промпта). Модуль их
не покрывает вовсе, не только не в MVP.

- **Администратор** — запускает Разбор характеристик и Генератор
  описаний вручную, подтверждает или правит каждый результат перед
  публикацией; никто другой не взаимодействует с этими двумя
  помощниками.
- **Гость / Покупатель** — пользуются Консультантом и Подбором диалогом
  напрямую на сайте, без входа в личный кабинет.
- **Менеджер** — не упомянут ни в одном `FR-AI-*` как действующая роль;
  «Помощник менеджера» из брифа — один из двух нераскрытых помощников
  выше, в модуль не входит.

## Поток данных

**Разбор характеристик (`FR-AI-001`) — пакетный, по запросу
Администратора:**
1. Администратор запускает разбор по одному или нескольким Товарам
   сразу (не поштучно) — текст описания Товара уходит провайдеру.
2. Провайдер возвращает предложенные значения характеристик (материал,
   цвет, размер, механизм — набор зависит от Категории). Значение, не
   найденное в тексте, остаётся пустым — не подставляется по умолчанию.
   Значение вне справочника Категории помечается «требует решения», не
   записывается как есть.
3. Ничего не публикуется само — Администратор видит предложенные
   значения и подтверждает каждое перед тем, как они попадут в карточку
   Товара.
4. Исходный текст описания не меняется этим процессом.

**Генератор описания (`FR-AI-002`) — по одному Товару, по запросу:**
1. Администратор вводит краткие данные (категория, материал, размер,
   механизм и т. п.) → провайдер возвращает черновик текста.
2. Черновик хранится отдельно от публикуемого описания до явного
   действия «сохранить»; черновик не может содержать характеристики,
   которых Администратор не указал во входных данных.

**Консультант в чате (`FR-AI-003`) — объединяет исходный `FR-AI-004` и
инфо о заказе (`ADR-051`, отход от ТЗ по прямому запросу владельца
продукта). Один помощник на три сценария, по каждому сообщению
Покупателя:**
1. Покупатель вводит сообщение в виджете чата на сайте.
2. **Доставка/оплата/возврат/гарантия/шоурум** — провайдер отвечает по
   правилам и текстам страниц `content_pages`, зашитым в системный
   промпт (собирается заново на каждый запрос — правка `ADR-019`,
   `ADR-050`). Вопрос вне этих тем и вне двух сценариев ниже → помощник
   не пытается ответить, предлагает связаться с Менеджером (телефон +
   WhatsApp).
3. **Подбор товара** (был `FR-AI-004`) — если Покупатель описывает,
   что ищет, провайдер получает снимок каталога **только опубликованных
   Товаров с подтверждёнными характеристиками** (`specs_status='confirmed'`
   — то есть там, где `FR-AI-001` уже прошёл) и указывает slug ОДНОГО
   наиболее подходящего Товара в структурированном ответе; сервер
   проверяет slug по БД и сам собирает карточку (название/цена/
   описание/ссылка на карточку) из реальных данных — модель не может
   подделать факты о Товаре. Подходящего нет → `product_slug` не
   передаётся, показывается только текст, никогда не подставляется
   Товар «на всякий случай».
4. **Инфо о заказе** — Покупатель называет номер заказа и телефон/
   email. Сервер детектирует это регэкспом ДО вызова модели и сам
   сверяет оба значения с БД (номер И контакт обязаны совпасть) —
   отвечает готовым шаблоном (статус/сумма/дата/способ получения) или
   общим отказом без утечки факта существования заказа. **Эта ветка
   никогда не вызывает провайдера** — данные Заказа физически не
   покидают сервер, в отличие от подбора товара и обычных вопросов.
5. Ответ публикуется сразу, без ревью человеком — жёстко ограниченный
   круг тем и обязательная серверная проверка (`product_slug`,
   контакт заказа) заменяют ревью содержательным ограничением
   ввода/вывода.
6. Диалог не связывается с личным кабинетом и не запоминается между
   визитами.

**2-я очередь — тот же принцип, вне текущей фазы:**
- SEO-тексты Категорий (`FR-AI-005`) — черновик по аналогии с
  `FR-AI-002`, запускается тем же техническим механизмом.
- Смысловой поиск (`FR-AI-006`) — дополняет точный текстовый поиск
  (`FR-SRCH-*`) результатами по смыслу запроса; как и `FR-AI-004`,
  зависит от `FR-AI-001` (нужны подтверждённые характеристики).

## Ключевые бизнес-правила

**Маршрутизация провайдера по классу задачи, не по помощнику
(`BR-AI-001`).** Не «Консультант использует провайдера X», а «класс
задачи X использует провайдера, разрешённого для этого класса» —
конфигурация привязана к классу, не к конкретной функции, и смена
провайдера не должна требовать изменения кода (правило 3).
- **Обезличенные данные о товарах** (текст описания, краткие данные
  Администратора) — `FR-AI-001`, `FR-AI-002`, а по аналогии и
  `FR-AI-005` — любой провайдер, включая зарубежный.
- **Пользовательский ввод** (текст вопроса/запроса Покупателя) —
  `FR-AI-003`, `FR-AI-004`, а по аналогии и `FR-AI-006` — российский
  провайдер по умолчанию. Не потому что этот текст признан
  содержащим ПДн, а потому что он **не признан безусловно
  обезличенным** (правило 2) — предупреждение в интерфейсе не
  фильтрует и не маскирует то, что Покупатель может ввести
  добровольно.
- **С программно приложенными персональными данными** (имя, телефон,
  адрес, состав заказа) — только российский провайдер, но этот класс
  не используется ни одним из `FR-AI-001…004`: ни один помощник не
  передаёт эти поля программно. Единственный канал, которым ПДн
  теоретически попадают к провайдеру, — если Покупатель сам напишет
  их текстом в чате; это остаточный риск, не программная передача, и
  интерфейс только предупреждает, не блокирует.

**Ничего не публикуется без ревью там, где ошибка стоит репутации, и
публикуется сразу там, где ответ ограничен рамками (`FR-AI-001/002`
vs `FR-AI-003/004`).** Не единое правило «всегда проверять человеком»
— два разных режима по разной причине:
- Разбор характеристик и Генератор описаний пишут в карточку Товара,
  которую видят все посетители постоянно — 100% ревью Администратором
  перед публикацией, без исключений.
- Консультант и Подбор диалогом отвечают в моменте одному Покупателю —
  публикуются сразу, но их пространство ответов жёстко ограничено
  (только опубликованные страницы/FAQ для Консультанта, только
  реальные карточки каталога для Подбора) — это подменяет ревью
  постфактум структурным ограничением вопроса/ответа.

**Ни один помощник не блокирует основной сценарий покупки
(`AC-06`, раздел 11.8, «обязательное требование»).** Недоступность
провайдера — это отключение конкретного помощника, никогда сбой
покупки:
- `FR-AI-001` — Товар остаётся в очереди «требует разбора»,
  Администратор вводит характеристики вручную.
- `FR-AI-002`/`FR-AI-005` — Администратор пишет текст вручную,
  создание/публикация не блокируется.
- `FR-AI-003` — виджет чата показывает сообщение о недоступности,
  телефон и кнопку WhatsApp; остальной сайт не блокируется.
- `FR-AI-004` — блок подбора скрывается или показывает «недоступно»;
  обычный каталог с фильтрами продолжает работать без ограничений.
- `FR-AI-006` — откат на обычный текстовый поиск (`FR-SRCH-*`).

**Порядок зависимости: структурирование раньше функций, которые на
нём работают.** `FR-AI-004` (правило 1) и `FR-AI-006` (правило 1) не
могут предложить Товар Категории, для которой `FR-AI-001` ещё не
подтверждён Администратором. Граница — факт подтверждения
характеристик, не календарная дата и не системный статус ожидания.

**Общий месячный бюджет — один лимит на всё, без автоотключения
(`BR-AI-001` правило 5, `NFR-AI-*`).** 5 000 ₽/мес суммарно на все
классы задач и всех помощников сразу, не по помощнику отдельно. При
исчерпании лимита помощники **продолжают работать** — Владельцу
приходит предупреждение, решение остановить принимает он сам, не
система автоматически.

> **Реализовано Таском 8 Фазы 9 (`/admin/ai`, только `admin`).**
> Превышение проверяется после каждого успешного вызова
> (`notifyIfAiLimitExceeded()`, `Services/Ai/ai.php`) — баннер в Панели
> + `logWarning()` + письмо каждому `role='admin'`, не чаще раза в
> календарный месяц (`settings.ai_limit_notified_month`, `Q-027`).
> «Решение остановить принимает Владелец сам» реализовано как три
> отдельных тумблера — `specs`/`description`/`consultant`
> (`aiAssistantEnabled()`), не общий рубильник на весь модуль: можно
> остановить конкретного помощника, не трогая остальных. Четвёртого
> тумблера для «Подбора Товара» нет — с `ADR-051` это часть
> `consultant`, отдельного включения/выключения не имеет (`ADR-052`).

**Данные Покупателя не идут на обучение моделей провайдера
(`BR-AI-001` правило 4).** Обязательное условие договора с любым
выбранным провайдером — проверяется на этапе выбора провайдера
(`AS-006`), не реализуется кодом сайта напрямую.

**Логи переписки чат-помощников хранятся 3 месяца, без фильтрации
ПДн (`NFR-AI-*`, решения `Q-026`/`Q-028`).** Касается только
`FR-AI-003`/`FR-AI-004` (диалоговый ввод) — `FR-AI-001`/`FR-AI-002` не
ведут лог переписки, там нет диалога с Покупателем. Срок — 3 месяца,
не «пока не удалят вручную» и не бессрочно.

## Граничные случаи из сценариев ТЗ (раздел 7)

Раздел 7 (UC-01…UC-05) не содержит отдельного сценария для модуля
`AI` — ни один из основных ходов или отклонений UC-01…UC-05 не
упоминает Консультанта или Подбор диалогом явно. Это не пробел ТЗ:
модуль сознательно вынесен из основного сценария покупки (`AC-06`) и
описан собственным набором критериев приёмки внутри каждого `FR-AI-*`
(раздел 8.19) и отдельным приёмочным сценарием `AC-06` (раздел 14) —
именно они и есть источник граничных случаев для этого модуля, а не
раздел 7:
- Провайдер недоступен во время сессии Покупателя (`AC-06`) — блок
  Консультанта отключается, оформление Заказа проходит без ошибок.
  Тот же принцип по каждому из четырёх MVP-помощников — см. правило
  «не блокирует основной сценарий» выше.
- Описание Товара не содержит одну из характеристик — поле остаётся
  пустым, карточка не считается ошибочной (`FR-AI-001`).
- Предложенное значение не входит в справочник Категории —
  «требует решения», не записывается автоматически (`FR-AI-001`).
- Вопрос Покупателя вне круга тем документов — предложение позвонить
  Менеджеру, помощник не пытается ответить по общим знаниям
  (`FR-AI-003`).
- Вопрос про гарантийный ремонт конкретного (уже купленного) Товара —
  помощник не определяет статус по имени/номеру заказа, предлагает
  звонок Менеджеру, потому что данные Заказа ему не передаются
  (`FR-AI-003`).
- Запрос на подбор ничего не находит — пустое состояние с explicit-
  предложением каталога/Менеджера, не подстановка «похожего» Товара
  (`FR-AI-004`).
- Категория, для которой характеристики ещё не подтверждены — не
  участвует в подборе/смысловом поиске (`FR-AI-004`, `FR-AI-006`).

## Связанные таблицы БД

`.docs/database.md` **не содержит** ни одной таблицы для этого модуля
на сегодня — в базовых таблицах нет:
- очереди «Товар требует разбора характеристик» и признака
  «характеристики подтверждены» (нужен для `FR-AI-001` правило 4 и
  для зависимости `FR-AI-004`/`FR-AI-006` правило 1 — «Товар без
  подтверждённых характеристик не участвует в подборе»);
- хранилища черновика описания Товара/Категории до подтверждения
  (`FR-AI-002`, `FR-AI-005`) — сейчас у `products.description` и
  будущей таблицы категорийного контента нет отдельного поля-черновика;
- лога переписки Консультанта/Подбора (`FR-AI-003`/`FR-AI-004`,
  3 месяца хранения, `NFR-AI-*`).

Это не решается на шаге `sdd-modules` — правило 1 системного промпта
запрещает изобретать структуру таблиц вне ТЗ, а раздел 6
(доменная модель) этот модуль не описывает вовсе (AI — процесс, не
сущность из глоссария 6.1). Проектирование этих таблиц — задача
следующего прохода `sdd-schema` или `phase-init` для Фазы 9,
зафиксировано как открытый вопрос ниже.

Не входит в этот модуль (пограничные, но отдельные модули):
- Справочник характеристик по Категориям (материал/цвет/размер/
  механизм как поля `product_variants` и будущий справочник значений
  для фильтров) — модуль `CAT`/`CARD` (Фаза 1); `AI` только
  предлагает значения в эти поля, не определяет их набор.
- Статические страницы «Доставка и оплата», «Возврат и гарантия», FAQ —
  модуль `CNT` (Фаза 8). По модели ТЗ `AI` читал бы их контент без
  собственной копии; в реализации этого проекта (`ADR-019`) копия в
  виде текста всё же есть — внутри системного промпта Консультанта,
  обновляется вручную при изменении `CNT`, не автоматически.
