# Схема БД

> Этот файл — детальное описание всех таблиц.
> Агент читает его при планировании тасков связанных с БД.
> Синхронизируй с `database/install.php`.

---

## Как устроен этот файл

Ниже — **базовый набор таблиц**, который есть почти в любом интернет-магазине
(каталог → корзина → заказ). Это часть шаблона, а не схема конкретного проекта:
таблицы, колонки, FK и индексы здесь — стартовая точка, рассчитанная сразу на
каталог порядка **10 000–50 000 товаров**, чтобы не переделывать индексацию
задним числом.

**Реальный масштаб проекта ДомФорм** (раздел 11.2 ТЗ, `NFR-LOAD-*`) —
на порядки меньше: ≈80 Товаров сейчас, 150–200 через год, 1–2 Заказа в неделю
сейчас / 3–4 в день через год, ≤50 одновременных сессий в пик. Базовые
индексы (FULLTEXT, `category_id`+`is_active` и т.п.) не мешают на таком
объёме — оставлены как есть. Но при выборе индексов для **новых** таблиц
ниже это единственная реальная точка отсчёта: не переносим 50k-паттерны
туда, где не больше пары тысяч строк.

При адаптации под свой магазин:
- базовые таблицы обычно **не удаляют**, а расширяют колонками
  (`brand_id`, `weight`, `barcode` и т.п.);
- специфичные для проекта таблицы добавляй в раздел «Дополнительные таблицы»
  по тому же формату (колонка | тип | назначение) и зеркаль их в
  `database/install.php` в порядке зависимостей (сначала родитель, потом
  потомок — `categories` → `products` → `order_items`).

**Отступление от этого принципа в проекте ДомФорм:** `products.sku`,
`products.price`, `products.stock_quantity` и `products.category_id`
**удалены**, не расширены — доменная модель ТЗ (раздел 6.1, 6.2) требует
отдельной сущности «Вариант товара» с собственными артикулом/ценой и
M:N связи Товар↔Категория, а не 1:N. Оставить старые колонки
неиспользуемыми означало бы два источника истины по цене (`products.price`
и `product_variants.price`) — прямое нарушение `general.md`. Решение
зафиксировано как `ADR-004`/`ADR-005` в `planning-log.md`.

### `password_resets` _(новая — `ADR-027`)_

Восстановление пароля (`FR-AUTH-003`) — Покупатель, забывший пароль,
получает по email одноразовую ссылку со сроком действия, без участия
Менеджера/Администратора.

| Колонка | Тип | Назначение |
|---------|-----|------------|
| id | INT PK AUTO_INCREMENT | |
| user_id | INT NOT NULL, FK → users.id, ON DELETE CASCADE | |
| token_hash | CHAR(64) NOT NULL UNIQUE | sha256 от случайного токена (32 байта из `random_bytes`) — в БД хранится только хэш, сам токен уходит только в ссылку письма, как пароль |
| expires_at | DATETIME NOT NULL | момент создания + 60 минут |
| used_at | DATETIME NULL | одноразовость — заполнено после успешной смены пароля, повторное открытие той же ссылки отклоняется |
| created_at | TIMESTAMP DEFAULT NOW | |

**Индексы:** `UNIQUE(token_hash)` — поиск по токену из ссылки;
`INDEX(user_id)` — аннулирование прежних запросов при новом

### `remember_tokens` _(новая — `ADR-028`)_

«Запомнить меня» (`FR-AUTH-004`) — вход сохраняется между визитами на
устройстве дольше, чем живёт cookie сессии (без этого GC сессий на
shared-хостинге разлогинивает раньше, чем ожидает Покупатель).

| Колонка | Тип | Назначение |
|---------|-----|------------|
| id | INT PK AUTO_INCREMENT | |
| user_id | INT NOT NULL, FK → users.id, ON DELETE CASCADE | |
| selector | CHAR(24) NOT NULL UNIQUE | публичная часть значения cookie — по ней ищем строку без сканирования таблицы |
| token_hash | CHAR(64) NOT NULL | sha256 секретной части cookie; сравнение — `hash_equals()`, не `===` (защита от timing-атаки) |
| expires_at | DATETIME NOT NULL | момент создания + 30 дней |
| created_at | TIMESTAMP DEFAULT NOW | |

**Индексы:** `UNIQUE(selector)` — поиск токена при авто-входе;
`INDEX(user_id)` — удаление всех токенов пользователя при выходе/смене
пароля

> Токен cookie хранится как пара `selector:secret`, не единой строкой —
> `selector` ищет строку по индексу, `secret` (в БД — только его хэш)
> сверяется через `hash_equals()`. Один `token_hash` без `selector`
> заставил бы перебирать все строки таблицы, сравнивая хэши, либо искать
> по самому хэшу — тот же класс утечки по времени сравнения, которого
> избегает пара selector/validator.

### `products`

Товар — общая карточка (название, описание), одна на все свои Варианты
(раздел 6.1 ТЗ: «имеет общее название и текстовое описание, единое для
всех своих Вариантов»). Цена, артикул, остаток и фото — на уровне
`product_variants`, не здесь (`ADR-004`).

| Колонка | Тип | Назначение |
|---------|-----|------------|
| id | INT PK AUTO_INCREMENT | |
| name | VARCHAR(200) NOT NULL | |
| slug | VARCHAR(220) NOT NULL UNIQUE | |
| description | TEXT NULL | |
| is_active | TINYINT(1) NOT NULL DEFAULT 1 | товар не удаляют физически, а деактивируют |
| is_featured | TINYINT(1) NOT NULL DEFAULT 0 | ручная отметка «хит продаж» Менеджером/Администратором для блока Главной (`FR-HOME-004`) — не расчёт по продажам (ТЗ прямо: отдельного справочника продаж нет, раздел 10.1); по аналогии с `product_variants.is_showroom_sample`. Колонки не было в схеме, найдено ревью перед `phase-init` (`ADR-024`, `Q-DEV-010`) |
| created_at | TIMESTAMP DEFAULT NOW | |
| updated_at | TIMESTAMP DEFAULT NOW ON UPDATE CURRENT_TIMESTAMP | |

**Удалено относительно базового шаблона** (`ADR-004`, `ADR-005`):
`sku`, `price`, `stock_quantity` → переехали в `product_variants`;
`category_id` → переехал в `product_categories` (M:N).

**Индексы:**
- `INDEX(is_active)` — листинг активных товаров (фильтр по категории теперь
  идёт через join с `product_categories`, см. ниже)
- `INDEX(is_featured)` — отбор блока «Хиты продаж» Главной (`FR-HOME-004`),
  тот же паттерн, что `INDEX(is_showroom_sample)` у `product_variants`
- `FULLTEXT(name, description)` — поиск; `LIKE '%...%'` не использует индекс

### `product_variants` _(новая — `ADR-004`)_

Вариант товара (раздел 6.1, 6.2 ТЗ): собственный артикул, материал, цена,
срок изготовления; цвет на цену/артикул не влияет — это атрибут фотографий
(см. `variant_images` ниже), не отдельная колонка здесь.

| Колонка | Тип | Назначение |
|---------|-----|------------|
| id | INT PK AUTO_INCREMENT | |
| product_id | INT NOT NULL, FK → products.id, ON DELETE CASCADE | |
| sku | VARCHAR(64) NOT NULL UNIQUE | артикул варианта (было на `products`) |
| material | VARCHAR(150) NOT NULL | материал обивки/корпуса (раздел 6.2) |
| mechanism_type | VARCHAR(150) NULL | механизм/тип конструкции — только там, где применим к подкатегории (раздел 6.2: «если применим»), иначе NULL |
| price | DECIMAL(10,2) NOT NULL | никогда FLOAT — см. `php.md`; между Вариантами различается (раздел 6.2: экокожа дороже на 15–20%) |
| production_time | VARCHAR(100) NOT NULL | срок изготовления как текст («2–3 недели»), не число дней — точный формат не задан ТЗ на этом шаге (раздел 8 не читался) |
| is_showroom_sample | TINYINT(1) NOT NULL DEFAULT 0 | отметка «Выставочный образец» — 0..1 физический экземпляр на Вариант одновременно (раздел 6.1) |
| discount_percent | DECIMAL(5,2) NULL | скидка на Вариант — процент, не сумма (`BR-002`); NULL = скидки нет; включается/снимается вручную Менеджером/Администратором, без даты начала/окончания |
| is_active | TINYINT(1) NOT NULL DEFAULT 1 | |
| created_at | TIMESTAMP DEFAULT NOW | |
| updated_at | TIMESTAMP DEFAULT NOW ON UPDATE CURRENT_TIMESTAMP | |

**Индексы:**
- `INDEX(product_id)` — варианты одного товара
- `INDEX(price)` — сортировка/фильтр по цене (было на `products`)
- `INDEX(is_showroom_sample)` — отбор выставочных образцов (`BR-004`: остаток
  покупателю не показывается, вместо него — этот статус)
- `INDEX(material)` — префиксный поиск `LIKE 'q%'` по материалу (`FR-SRCH-002`,
  Таск 5 Фазы 1, `ADR-032`)

> Остатка/количества нет ни у одного Варианта, кроме отметки Выставочного
> образца (`BR-004`) — обычные Варианты изготавливаются под заказ без
> предела. «Набор доступных цветов» варианта (раздел 6.1) отдельной
> колонкой/таблицей не хранится — это множество различных `color` в
> `variant_images` (раздел 6.2: по цвету различаются только фотографии).

### `reserves` _(новая — `ADR-007`)_

Резерв Выставочного образца (раздел 6.1, `BR-003`): не системный таймер —
устно согласованный срок, снимается вручную Менеджером или автоматически
при отмене/доставке заказа.

| Колонка | Тип | Назначение |
|---------|-----|------------|
| id | INT PK AUTO_INCREMENT | |
| order_item_id | INT NOT NULL, FK → order_items.id, ON DELETE CASCADE, UNIQUE | одна Позиция заказа — не более одного Резерва |
| product_variant_id | INT NOT NULL, FK → product_variants.id, ON DELETE CASCADE | дублируется из `order_items` намеренно — конкуренция за образец (`BR-003`, «кто первым внёс предоплату») проверяется часто и не должна каждый раз идти через join |
| status | ENUM('active','released','fulfilled') NOT NULL DEFAULT 'active' | `active` — держится; `released` — снят вручную (отмена заказа или Покупатель не забрал к согласованному сроку); `fulfilled` — списан при переходе Заказа в «Доставлен/Собран» |
| active_variant_id | INT GENERATED ALWAYS AS (IF(status = 'active', product_variant_id, NULL)) VIRTUAL | служебная колонка только для уникального индекса ниже — приложение её не читает и не пишет напрямую |
| agreed_until | DATE NULL | срок, устно согласованный Менеджером с Покупателем (`BR-003`: «без системного таймера») — не используется для автоматического снятия |
| created_at | TIMESTAMP DEFAULT NOW | момент создания — переход связанного Заказа в «Подтверждён» с первой предоплатой (`BR-003`) |
| released_at | TIMESTAMP NULL | момент снятия/списания |

**Индексы:**
- `INDEX(product_variant_id, status)` — быстрый поиск активного резерва по
  Варианту при проверке конкуренции (`BR-003`)
- `UNIQUE(active_variant_id)` — защита от гонки на уровне БД, см. ниже

> **Не более одного `active`-резерва на Вариант одновременно — обеспечивается
> на уровне БД, не только проверкой в Model (`BR-003`: конкуренция решается
> по факту оплаты — два подтверждения предоплаты по одному Варианту могут
> прийти практически одновременно, это тот же класс гонки, что оверселлинг
> остатка в `general.md`, «прочитать, потом вставить» не защищает).**
> Решение: виртуальная generated column `active_variant_id` равна
> `product_variant_id`, когда `status='active'`, и `NULL` во всех остальных
> случаях — MySQL 8 поддерживает `UNIQUE`-индекс на `VIRTUAL` generated
> column, а `UNIQUE` допускает множество `NULL`, поэтому ограничение
> срабатывает только для активных резервов одного Варианта. Вторая попытка
> вставить активный резерв на тот же Вариант получает ошибку дублирования
> ключа (SQLSTATE 23000) — Model обязана перехватывать её и трактовать как
> проигрыш конкуренции (`BR-003`, UC-02 отклонение 2а), а не как системный
> сбой.

## Правила

- Все `user_id` FK → `ON DELETE CASCADE`, **кроме `orders.user_id`**
  (`SET NULL` — история заказов должна пережить удаление аккаунта)
- Все таблицы → `ENGINE=InnoDB`, `utf8mb4_unicode_ci`
- Пароли никогда в открытом виде
- Деньги — только `DECIMAL(10,2)` (скидка — `DECIMAL(5,2)` как процент, не
  сумма, см. `product_variants.discount_percent`), никогда `FLOAT`/`DOUBLE`
- Товары и Варианты не удаляются физически — деактивируются `is_active = 0`
  (сохраняет ссылочную целостность с `order_items` и историю заказов)
- Поиск по названию/описанию — только через `FULLTEXT`, не `LIKE '%...%'`
- Листинг каталога — всегда с пагинацией; на страницах вглубь каталога
  (когда `OFFSET` большой) предпочитать keyset-пагинацию
  (`WHERE id > :last_id LIMIT :n`) вместо `LIMIT :offset, :n`, которая на
  больших таблицах линейно замедляется с ростом смещения — при реальном
  масштабе ДомФорм (≤200 товаров, раздел 11.2 ТЗ) не критично, но остаётся
  общим правилом шаблона
- Ни одна таблица не получает `external_id`/`synced_at` — раздел 10.1 ТЗ
  прямо фиксирует отсутствие внешней системы (учётной системы/CRM нет,
  «Админка сайта — единственное место, где данные вообще существуют»);
  добавлять место под синхронизацию, которой не будет, — домысел
